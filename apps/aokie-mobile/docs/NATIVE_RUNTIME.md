# Companion native runtime

This document describes the native credential, Android wake/call, permission,
and platform boundaries. It is deliberately separate from protocol-v2 call
authority: push and operating-system call surfaces are hints only.

## Media and routing model

Companion is a microphone/speaker endpoint, whether it runs on Windows or on a
phone. Encrypted WebRTC media flows directly between Aokie Desktop and
Companion, or through the configured TURN relay. FormLogic (or a compatible
custom server) handles authentication, signalling, routing, and arbitration;
it does not receive or mix call PCM.

Running the Windows Companion on the same computer as Aokie Desktop is
supported. Android is not categorically excluded from running on the cellular
gateway handset. That particular topology must be tested because the handset's
HFP/cellular route and its WebRTC route can contend for the same audio devices.
A local signalling server does not remove that operating-system audio-route
constraint.

## Managed credential lifecycle

- The OAuth authorization code flow, PKCE verifier, access token, refresh
  token, and protocol-v2 admission remain in Rust/native code. React receives
  no credential.
- Windows stores the rotating refresh token and minimal restart descriptor in
  Credential Manager.
- Android stores them as AES-256-GCM ciphertext under `noBackupFilesDir`. The
  encryption key is generated by Android Keystore, is non-exportable, and uses
  the logical record key as authenticated additional data.
- Startup restore re-fetches and re-verifies signed discovery, validates the
  deployment/app/device binding, immediately rotates the refresh token, and
  reacquires a short-lived admission before reconnecting.
- Invalid, revoked, or unpersistable refresh rotation deletes the native
  session and requires sign-in. No plaintext or WebView-storage fallback is
  permitted.

Native mobile account calls (`bootstrap`, `history`, `routing`, and
`availability`) use that same active session. Their URLs are constructed from
the verified OAuth-resource origin and a fixed `/api/aokie-companion/mobile/`
route allowlist. Rust sends the bearer, refreshes before expiry, refreshes and
retries once on HTTP 401, disables redirects, bounds request/response bodies,
requires JSON/HTTP 200, and parses deny-unknown typed schemas. React receives
only redacted membership/device metadata, capability enums, team availability,
redacted activity/session history, and push endpoint fingerprints; it never
receives the OAuth token or a push token/handle.

Windows audio endpoints are enumerated locally through libwebrtc's platform
audio module. React receives only bounded local labels and opaque endpoint
GUIDs. A selection is revalidated against a fresh enumeration and can change
only while native media is idle; the next peer applies it before playout or
recording starts. Android and iOS report routing as `system_managed` because
their call-session route APIs, not a desktop-style GUID selector, own routing.

The iOS implementation is intentionally build-gated. Source under
`src-tauri/native/ios/AokieCompanionRuntime` provides a Keychain credential
envelope using `AfterFirstUnlockThisDeviceOnly`, strict pre-UI PushKit offer
storage, CallKit answer/winner fencing, and AVAudioSession permission,
interruption, and route hooks. There is no generated iOS project, native Tauri
plugin/FFI binding, Apple toolchain, provisioning profile, or APNs entitlement
in this Windows workspace, so none of that source has been compiled, signed,
or device-verified. Until those gates are completed, the running app reports
iOS secure storage/background calls unavailable instead of simulating success.

## Android Firebase configuration

FCM is optional at compile time. The source tree contains no Firebase project
credential. A production build enables it by placing the project-specific file
at:

```text
src-tauri/gen/android/app/google-services.json
```

The file is gitignored. The Google Services plugin is applied only when the
file exists. Without it, the app still builds and foreground operation works;
runtime diagnostics report `fcm_configuration_required`.

The FCM registration token is encrypted in the native store and never returned
to React. After managed sign-in/restore, a native watcher consumes the token and
uses the same native OAuth refresh/one-retry path to PUT the exact
`/api/aokie-companion/mobile/devices/{oauthDeviceId}/push-endpoints/fcm` route. It accepts only a
strict redacted endpoint response, verifies the server fingerprint against the
local token, and stores only that fingerprint as the registration marker. FCM
rotation removes the marker and triggers re-registration; logout sends the
idempotent DELETE, clears both native records, and asks Firebase to invalidate
the provider token. Without Firebase configuration, diagnostics remain
truthfully `configuration_required`; while a token or endpoint is pending they
report the corresponding pending state, and a matching marker reports
`registered`.

## Data-only push contract (schema 1)

All values are FCM data strings. Unknown keys reject the entire message. Push
must not include OAuth/admission/lease credentials, SDP, ICE, captions, or a
caller phone number.

`voice_offer` allows exactly:

```json
{
  "aokieClass": "voice_offer",
  "schemaVersion": "1",
  "eventId": "event_123",
  "offerId": "offer_123",
  "appId": "app_123",
  "callId": "call_123",
  "callEpoch": "7",
  "ownerEpoch": "4",
  "expiresAt": "1784167200"
}
```

The offer must expire in the future and no more than five minutes after
receipt. IDs are 1-200 characters using letters, digits, `-`, `_`, `.`, or
`:`. Epochs are bounded to JavaScript's maximum safe integer. A different
pending offer may replace the current one only when `callEpoch` advances.

`voice_offer_cancel` allows exactly `aokieClass`, `schemaVersion`, `eventId`,
`offerId`, and `reason`. `reason` is 1-120 printable characters. Cancellation
closes only the Companion leg; it cannot hang up the cellular caller.

`informational` allows exactly `aokieClass`, `schemaVersion`, `eventId`,
`title`, `body`, and `expiresAt`. Its lifetime is at most 24 hours. It uses a
normal informational notification channel and never a call channel.

## Android incoming-call authority

1. The exported-false FCM service validates and encrypts the offer before the
   WebView is involved.
2. A foreground phone-call service immediately publishes a high-importance
   private `CallStyle` notification and registers an incoming Core-Telecom
   call.
3. Answer changes native state to `answer_requested` and opens Companion. It
   does not request microphone permission, arm a track, or claim the call.
4. Only an exact signed protocol-v2 winner for the same `callId` and
   `callEpoch` changes the offer to `won`, activates the system call, and allows
   the normal fenced WebRTC talk path to request audio. Private consultation is
   a separate in-app assistance flow and cannot win or take over the caller.
5. Expiry, authoritative cancellation, lease loss, or a different first winner
   removes the notification and closes only the Companion leg.

The reconciliation JNI hook exists, but the server/gateway must still fan out
the exact winner/cancellation event and wire it to that hook. FCM is never the
source of winner authority.

## Permissions and diagnostics

Microphone and notification permission are separate:

- Monitor/listen-only mode never requests the microphone.
- Prepared consultation is receive-only. Active consultation requests the
  microphone only after Desktop has acknowledged software hold and the server
  has rotated the lease/owner epoch; its track terminates at Aokie, not caller SCO.
- Talk requests the microphone only after exact native call/lease fencing.
- While transmitting on Android, native code rechecks microphone permission
  every 500 ms. Denial or revocation disarms the track, clears the native live
  proof, and closes the local media peer immediately.
- Notification denial prevents an incoming-call surface but does not grant or
  imply microphone access.

Runtime capabilities expose only booleans/status strings, never secrets:
secure-storage availability, notification and microphone permission,
notification enablement, native-call infrastructure, FCM configuration/token
presence, endpoint-registration state, pending-offer presence, battery
optimization status, force-stop detectability, and the most recent bounded
native diagnostic code.

Android cannot reliably detect its own force-stop state while stopped, so the
diagnostic is explicitly `not_detectable`; the setup UI must not claim
otherwise.

## Required physical tests

- Android 8 through current supported Android versions, including Android 13+
  notification permission.
- Background, Doze, reboot, app update, FCM token rotation, and user force-stop.
- Offer expiry, duplicate/stale offer rejection, cancellation, and competing
  first-winner fan-out while the WebView is not running.
- Permission denial and mid-call revocation.
- Audio focus loss, wired/Bluetooth endpoint changes, speaker/earpiece routing,
  and the carrier-gateway handset HFP/WebRTC contention case.
- Process death during refresh rotation and during answer-before-winner.
- Real TURN relay and direct WebRTC media; signalling-server success alone is
  not a media-path test.

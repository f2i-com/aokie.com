# Aokie plugin contract

What the Aokie plugin owes the desktop that hosts it. The plugin protocol comes from
FormLogic Desktop, and OAIY Desktop hosts Aokie through the same protocol
(`pluginApiVersion` 1); "the host" below means either one.

**Canonical contracts:** the FormLogic repository
([f2i-com/formlogic.com](https://github.com/f2i-com/formlogic.com)) holds
`docs/AOKIE_PLUGIN_CONTRACT.md` (this plugin's command and event surface),
`docs/DESKTOP_PLUGIN_SDK.md` (the host protocol), `docs/PLUGIN_LIFECYCLE.md`,
`docs/FORMLOGIC_DESKTOP.md` and `docs/ADR_FORMLOGIC_DESKTOP.md`. OAIY records what it
provides in its own `docs/ecosystem/AOKIE_CONTRACT.md`. The local schema copies in
[`contracts/`](contracts/) are validated by this repo's tests
(`crates/aokie-plugin/tests/contract_schemas.rs`).

This repo owns the **Aokie Phone Bridge** plugin: the Bluetooth dongle and phone bridge
(WinUSB, HFP/SCO, MAP SMS, PBAP contacts). The plugin ships its own receptionist screen,
which the host shows as a page and as steps of its setup wizard. The business records,
flows and front desk app live in FormLogic, in the "Aokie Receptionist" starter.

## Structure

```
crates/aokie-core     Tauri-free native logic (no `tauri::` imports — CI-enforced).
                      Gradual home for: aokie_radio, msbc, aokie_dongle(+catalog),
                      database, ai traits/adapters, redact, retention, ...
crates/aokie-plugin   The plugin process: main.rs, rpc.rs (JSON-RPC 2.0 NDJSON stdio),
                      connector.rs (command dispatch), event_bridge.rs, outbox.rs, config.rs,
                      radio/ (the call loop), realtime_voice.rs (the Desktop realtime route)
  manifest.json       schemaVersion 4: commands, events, UI, modules and the setup wizard
  ui/receptionist/    The receptionist screen (plain JS, no build step)
```

## Manifest, protocol and delivery

- Manifest `crates/aokie-plugin/manifest.json` (installed as `plugins/aokie/manifest.json`) per `plugin-manifest.schema.json`: `schemaVersion` 4, id `aokie`, `pluginApiVersion:1`, `minDesktopVersion`. Beside the capabilities, connector commands, events, `ui` (the AI Receptionist nav entry and screen, the overview hero and status cards), `commands.journalled`, `data.externalInventory` and `serviceDefinitions` (`definitions/phone.json`), schemaVersion 4 adds `modules.provides: ["phone", "calendar"]` and a `setup` wizard (version 1, "Set up the AI Receptionist") of seven steps: `consent` (screen view `consent`; done when consent is enforced, Bluetooth is allowed and nothing blocks), `speech` (requirements: the `oaiy-voice` service and an engine language model), `dongle` (screen view `dongle`, only while `transportMode` is the dongle; done when `radio.initialized`), `pair` (screen view `phone`; done when a phone is connected and no pairing window or code is pending), `behaviour` (optional settings: `autoAnswer`, `bargeIn`, `agentHangup`), `business` (host action `calendar.business`) and `answer` (host action `phone.answerWithOaiy`). Hosts that read schemaVersion 4 enforce `minDesktopVersion`.
- Protocol: `plugin.init` (≤10 s), `plugin.health`, `plugin.shutdown`, `connector.request`; notifications `event.emit` (envelope per `desktop-event.schema.json`, `source:"aokie"`, stable `idempotencyKey = aokie:<correlationId>:<step>:v1`) and `log.emit` (redacted).
- Occurrence identity (AOK-EVENT-001): a step that can REPEAT under one correlation (radio lifecycle under `radio` — `dongle.ready`, `phone.connected/disconnected`, `hardware.error` — and per-call `audio.connected/disconnected`) appends an immutable per-incident occurrence id to the step (`aokie:radio:hardware.error.<occ12>:v1`), minted once at detection so replays keep one key while every new incident gets its own. Inbound SMS identity is `sms_<deviceAddr>_<mapHandle>` (stable per phone+message; re-fetches dedupe); a phone that sends no handle falls back to a fresh occurrence id.
- Local SQLite outbox (`aokie_outbox`, UNIQUE idempotency_key) written before emitting essential raw-record events; retry with backoff; `dead` surfaced via diagnostics. `sent` is terminal (ack/replay races can never move it backward; bookkeeping is generation-conditional), and a same-key/different-content insert is REJECTED and counted (`dongle.diagnostics → outbox.keyCollisions`) — it means a key-derivation bug, never a harmless duplicate.
- Dev/mock mode (`FORMLOGIC_DEV_MODE=1`): scripted call lifecycle events for integration tests.
- Never write non-protocol output to stdout; PII redacted in logs by default.

## Commands

- Commands (the manifest's `connectors[0].commands`): `dongle.list/getPreferred/setPreferred/installDriver/restoreDriver/removeCerts/diagnostics/reset`, `phone.status/startPairing/stopPairing/confirmPairing/listPaired/removePaired/connect/disconnect`, `call.current/switchboard/activate/answer/reject/hangup/operatorSpeak/configureAgent/dial`, `sms.threads/thread/send`, `settings.get/set`, `outbox.redrive`, `consent.get/set/revoke`. The journalled ones (`commands.journalled`) carry a request id, and a repeat returns the stored result. Hardware-dependent commands may return typed `command_failed` until wired; never fake success.
- Call-control result semantics (AOK-CTRL-001): RADIO-backed `call.answer/reject/hangup/operatorSpeak` results report ACCEPTANCE only — `{accepted: true, queued: true, operationId: "op_…", via: "radio"}`, never the final verb. The authoritative confirmation is the lifecycle event (`call.answered`, `call.ended`, the bot `call.turn.final` for speech — bot turns carry a `delivery` field: `complete|interrupted|operator_ended|error`; an interrupted/cut bot turn's `text` is a CONSERVATIVE estimated-audible prefix (delivery-truth §6.3: duration-weighted vs the synthesized total, floored to a word boundary — underclaimed, never overclaimed; the unheard remainder feeds the next reply's repair context instead)); an asynchronous failure emits `aokie.hardware.error` with `code: "control_failed"` (or `"speak_failed"`) + the `operationId` and `action`. Dev/mock results complete synchronously and keep their final verbs (plus `accepted: true`). `call.operatorSpeak` is REFUSED (typed `command_failed`) while the running radio's in-plugin agent owns replies. `call.operatorSpeak` also accepts optional `inResponseTo` (§9.2): the `turn` NUMBER of the caller turn the speech answers — when a NEWER caller turn already exists the command is refused with typed `stale_turn` and nothing is spoken; callers MUST treat `stale_turn` (and `stale_call`) as a benign skip, never as a failure that triggers fallback speech. `call.configureAgent {callId, persona?, greeting?}` (§9.3) applies a CALL-SCOPED persona/greeting overlay to the named call only — `callId` is REQUIRED (typed `stale_call` when it is not the current call), the overlay is wiped at the call boundary, and the durable `settings.set` path remains for caller-independent config.
- Dongle reset (`dongle.reset {}`, no fields, journalled): the software recovery `AokieRuntime::reset_transport()` — close and reopen the dongle's USB connection, HCI_Reset, re-initialise, page the phone that was connected. Result `{accepted: true, via: "software", phoneReconnected: boolean}` after waiting at most ~15 s for the controller's next `dongle.ready` and, when a phone was connected, its reconnect (`false` = not back yet; `phone.connected` follows). While a call is ringing or active (or a caller waits or is parked) it is refused with `command_failed` "a call is in progress: reset the dongle after it ends" and nothing is touched. Only the WinUSB dongle transport can reset; the dev mock answers `{…, phoneReconnected: true, simulated: true}`. The receptionist screen's Dongle tab has a "Reset the dongle" button for it.
- Refused texts (`sms.send`, since 2026-09-29): a send refused before it reaches the radio (an invalid number or body, a recipient on the blocked list, a short code or a service number, missing `sms` consent, no radio in real mode, the radio thread gone) returns its error and also emits the essential `aokie.sms.failed {messageId, to, reason, at, refused: true}`, so a FormLogic Messages row queued under the caller's `messageId` never stays queued. `to` is the value as given (at most 64 characters); no `messageId`, or one that cannot be an id, emits nothing. The key is a per-refusal occurrence (`aokie:<messageId>:sms.failed.<occ>:v1`), so a retry under the same `messageId` never collides. One send gets one outcome: a text the radio accepted is answered only by the radio's own `aokie.sms.sent` or `aokie.sms.failed`. `aokie.sms.sent` means the phone accepted the MAP push into its outbox, not that the carrier delivered it (see [HARDWARE.md](HARDWARE.md)).
- Who is never texted or rung (since 2026-10-09): a number on `blockedNumbers` is refused by `sms.send` and by `call.dial`, whoever asks (the list is matched as screening matches a caller: the last nine digits, of six or more); and `sms.send` refuses a short code or a service number (fewer than seven digits; eight digits beginning with 1, such as Australia's 19xx xxxx premium numbers; either with `+61` or `0011 61` in front). Both are checked before consent and before the radio, so they also hold in warn mode and in the simulator. These refusals do not pass with time: the same send is refused again until the list or the number changes, so a host should not retry them.

## The receptionist screen in setup mode

- Setup mode: the host can show the receptionist screen as a step of its setup wizard. It marks the document `<html data-oaiy-setup="<view>">` before first paint and defines `PluginHost.setup` (`context`, `progress`, `done`, `fail`, `finish`). The screen then shows only that view's tab (`consent`, `dongle` or `phone`), without its tab bar or Overview, reports `progress` as the step moves, and calls `done` once the step's state holds: consent recorded and enforced, the radio up on the dongle, or a paired phone connected. It calls `fail` only for an error the person must see in the wizard. Without `PluginHost.setup` the screen is exactly the normal page. `scripts/check-receptionist-setup.mjs` checks both modes with a stub host.

## Calls on the OAIY route

- The OAIY route (`realtimeVoiceMode=desktop_realtime` with provider `oaiy`): OAIY hears, speaks and decides for every call it is given, and no path counts on Aokie's own speech stack. Its `formlogic.realtime.start` / `begin` `instructions` are the persona alone (the saved one, or the call's `configureAgent` overlay), not Aokie's realtime wrapper, and an agent dial adds none of Aokie's outbound-call rules (its purpose and opening line travel as start fields): OAIY's agent has its own call rules. Aokie's fixed lines — a screened caller's screen / blocked message, the hold and queue announcements, the mid-call failure apology — are said in OAIY's voice through its speak mode (`"mode": "speak"`, the line as `greeting`: said once, no agent, caller unheard; `output_item_done` then `stop`), falling back to Aokie's own TTS where present, else silence (the apology tries OAIY once with a 2.5 s wait). Screened callers are refused, never given to OAIY's agent; manager-number, already-answered and hold-promoted callers go to OAIY; the automatic hold juggle runs when a voice is there for its lines; an agent dial whose session cannot start is ended before the callee answers (`hardware.error` `control_failed`, `action: "call.dial"`); a mid-call OAIY failure ends in a hangup and `aokie.hardware.error {code: "realtime_failed", callId, route: "oaiy", apologized, apologizedWith?}`. `formlogic.realtime.start` carries the additive `direction`, `from`, `callerName`, `purpose`, `openingLine` there, each only when known. Other providers are unchanged (full wrapper, local TTS for fixed lines).

## Outbound calls and the manager line

- Outbound calling (Phase 2, call-policy spec): `call.dial {number, openingLine, purpose?}` — `openingLine` (1–500 chars, REQUIRED) is spoken VERBATIM at remote pickup via the greeting slot; `purpose` grounds the agent. Guardrails refuse typed BEFORE the radio: `outboundEnabled` kill switch (default OFF), local `quietHoursStart/End` (default 21→8; equal = disabled), persisted `maxDailyDials` (default 20, per operator-local day, counted pre-dial). Lifecycle: `aokie.call.outbound.dialing {callId, to, purpose?, at}` then the normal family with the same callId; `call.ended` carries `direction: "outbound"` + outcome `completed|no_answer|failed`. Outbound calls never mint `caller_id` events (the personalize/whitelist flows must not run against our own dial), are never screened, and a handset-originated (owner-dialed) call is observed silently — no greeting, no transcription.
- Manager line (Phase 3, call-policy spec): inbound callers digit-matching the `managerNumbers` setting bypass screening, get the manager greeting/persona, and lookups run name-inclusive (`manager: true` in the plugin's `flow.run` input — caller-id truth, never model output). Writes require the spoken PIN: the agent marks a change request `[[MANAGER: …]]` (never spoken), the plugin asks for and verifies the PIN against `managerPin` by deterministic digit comparison (words or digits, 2 attempts; the PIN turn is recorded/captioned only as `[manager PIN redacted]` — including boundary flushes), then runs the host `manager-action-plan` flow and emits `aokie.manager.action {callId, summary, hasUpdate, updateId, update, at}` for the apply binding's durable write. Blank `managerPin` keeps the manager line read-only; a `[[MANAGER]]` marker on a non-manager call gets an honest spoken refusal. Since 2026-07-17 the marker is TAUGHT only on manager-number calls — an ordinary caller's prompt never mentions it (small models kept marking ordinary own-bookings questions as manager requests despite explicit exclusions; live calls 8c689f13 + 0576e7eb), so ordinary calls answer bookings questions from records/[[LOOKUP]]; the non-manager refusal handler remains as a safety net. `managerPin` is WRITE-ONLY (AOK-304A): `settings.set` seals it at rest (DPAPI on Windows) and `settings.get` NEVER returns it — instead it exposes `managerPinSet: bool` (and, for a single-key get of `managerPin`, `value: null` + `set: bool`), so a settings snapshot can't leak the PIN; the verifier compares in constant time. `aokie.call.ended` and `aokie.call.transcript.settled` additionally carry `manager: true` for manager-number inbound calls, so customer-facing post-call booking extraction can skip them (a manager-line change must never ALSO be mined as a new booking — live call a5c3f900 minted a duplicate + a kickoff SMS at the manager). This field is number classification only and grants no manager authority; every privileged read/write still requires the independent per-call PIN state.

## Call waiting, hold and the switchboard

- Call waiting (Phase 4; `holdAndCallWaiting` setting, default OFF): with the setting on, the radio advertises HFP three-way calling (BRSF bit 1) and negotiates `AT+CHLD=?` + `AT+CCWA=1` at SLC time — both probes are conditional (skipped unless the AG advertises three-way) and NON-FATAL on ERROR (a refusing phone loses only the capability, never the HFP connection). On negotiated connections a second caller during an active call is a WAITING EPISODE: the active call/session is untouched, and `aokie.call.waiting {callId, from, waitingCallId, at}` is emitted once per episode (`callId` = the ACTIVE call; `from` = the waiting number, `""` when withheld; `waitingCallId` = the stable identity `call.activate` accepts them under). Every knock also fires a read-only `AT+CLCC`; the parsed topology lands in `dongle.diagnostics → radio.callWaiting.lastClcc`. Without negotiation (setting off / unsupported phone) the legacy lost-`call,0` recovery behaviour is preserved byte-for-byte. Capability verdict is logged once per SLC — carrier provisioning cannot be proven at SLC time, only by a real waiting call.
- Screened knockers (Phase 4, user policy 2026-07-15): a knocking second caller whose id the screening policy rejects (blocked list, accept-filter miss, withheld id with rejectPrivate) is NEVER juggled or queued — they ring out at the network untouched, the FIFO cascade never serves them (a parked caller waits for their ring to clear instead), and their give-up leaves NO missed-call record or ring-back. On an IDLE line a screened caller is refused in one of two ways (since 2026-10-09). With their number known while the phone still rings and no message set for them (`blockedMessage` for a blocked number, `screenMessage` otherwise), the call is rejected there and never picked up: `aokie.call.ended {outcome: rejected, reason: screened, durationSeconds: 0}`, with no `aokie.call.answered`. The reject is a request to the phone: it is sent again after 1.5 s if the call still rings, and after another 1.5 s the call is answered and refused at the greeting instead (it then ends `completed` / `screened`). Otherwise (a message to say, a number that arrives only after the answer, a withheld one) it is the answer-then-screen flow as before: the message when there is one, then the hangup, ending `completed` / `agent_hangup` after about a second. Either way nobody is rung or texted back: neither outcome is `missed`. The aokie.call.waiting event still emits for observability.
- Unserved knockers (Phase 4): the waiting-ring promotion (active call ends → the knock becomes a normal incoming ring + auto-answer) fires ONLY when nothing is held — with a caller parked it is suppressed at the HFP layer (promoting would queue-jump the knocker past the held caller; live 2026-07-15) and the FIFO cascade serves the knock instead. A knocker whose episode ends UNCLAIMED (no session minted under their waitingCallId, no promotion matching their number, ~2.5s grace) gets an honest `aokie.call.ended {outcome: missed, reason: gave_up_waiting, durationSeconds: 0}` under the waitingCallId so missed-call follow-ups ring them back — previously they left no record at all.
- Hold-queue outcomes (Phase 4): a PARKED caller who hangs up before the receptionist returns gets an honest `call.ended` outcome — `abandoned_on_hold` when they had a real conversation before being held (greeted; the reason reads `hung_up_on_hold`) or `abandoned_in_queue` when they only ever heard the "please hold — you're next" line (`hung_up_in_queue`). FormLogic flows key follow-ups off exactly these: on-hold → apology SMS (never a callback that rings someone who chose to leave), in-queue → missed-call-style callback whose opening line apologises for the hold.
- Automatic hold & queue (Phase 4 slice 6; `autoHoldQueue` setting, default OFF, applies at radio start, requires `holdAndCallWaiting`): a knocking second caller is answered with a spoken juggle — the active caller hears "another call came in, one moment", the newcomer hears "please hold — you're next in the queue" and is PARKED, the first caller is resumed; parked callers are retrieved FIFO as calls end, with a spoken resume line ("thanks for holding — where were we") for mid-conversation callers and the promoted greeting for never-greeted ones. Every `AT+CHLD=2` is a verified toggle: the juggle pumps the indicator stream and fires an on-demand `AT+CLCC` (ControlCommand::QueryCalls) after each swap, judges the resulting topology (`judge_accept` / `judge_swap_back`, unit-tested), and converges every failure shape — a refused swap-back degrades to single-swap (the newcomer keeps the line, the first caller stays parked for auto-retrieve), a NEW knock arriving mid-juggle ALSO degrades — with a waiting call up CHLD=2 would ACCEPT the knocker instead of swapping (live round 6: the phone answered the stranger and sacrificed the held primary), so the swap-back is never sent while a knock is up and an unknown active-leg number judges as StrangerActive (close the lost primary honestly, park the newcomer, mint the stranger as the foreground) rather than ever being assumed a swap, a dead leg is closed with an honest `call.ended`, and the z49 both-legs-torn-down signature ends in a clean idle. Max ONE parked caller (HFP exposes one held slot); a third caller keeps ringing at the network until a slot frees, then joins the same flow.
- Switchboard (Phase 4, OPERATOR-DRIVEN — nothing switches automatically): `call.switchboard` returns `{foreground, waiting, parked, revision, switchInProgress, callHeldState}` (while consent has paused the radio it answers empty, like `call.current`: `foreground`, `waiting` and `parked` null, `revision` 0, `switchInProgress` false, `callHeldState` 0, and `radio: {running: false, status: "paused", paused: true, blockedBy: "consent", reason}`; that is only when the radio is known to have stopped: one that was told to stop for consent and never confirmed it (15 s) answers an error, for `call.current` too, saying a call may still be on it, so a reader that must know (OAIY's update check) holds back rather than reading "no call"; with no radio for any other reason it is still an error); `call.activate {callId, expectedRevision?}` makes the waiting or parked caller the foreground with exactly ONE `AT+CHLD=2` (the plain toggle — the only mode phones without indexed CHLD advertise; never blind-retried). Accepting a knock PARKS the current caller: their session leaves the tracker with no terminal events and their whole conversational context (history, manager PIN gate, pace, captions state) travels with them; the accepted caller becomes a REAL call under their `waitingCallId` (`call.incoming` → `call.caller_id` → `call.answered`, then the normal greeting + personalize machinery). Swapping back restores the parked context under a FRESH generation (the focus fence — pre-hold STT/LLM/TTS work reads stale by construction). Max ONE parked caller; a swap-back while a new caller is knocking is refused (CHLD=2 would accept the knock). If the foreground ends while someone is parked the plugin AUTO-RETRIEVES them; a parked caller who hangs up (callheld→0 outside our own ~4s switch window) gets an honest `call.ended`, and callheld→2 closes a foreground leg that ended without a CallTerminated edge (the call indicator stays 1 while a held leg lives). Device loss with a parked caller synthesizes their termination truthfully.

## Voice and transcripts

- Duplex floor + pacing (additive): caller `call.turn.final` events may carry `kind: "control"` when the utterance was a deterministic floor command ("wait"/"stop"/"slower"/"repeat that") handled by the in-plugin duplex coordinator — consumers should skip business handling for those turns. Speech from ANY origin (built-in agent, greeting, flow/operator `call.operatorSpeak`) runs through one span planner: bracketed pacing markers (`[[slow]]…[[/slow]]`, `[[rate=0.8]]…[[/rate]]`, `[[important]]…[[/important]]`, `[[WAIT]]`) are validated/clamped/stripped there and are NEVER spoken or recorded; phone-number/code digit runs are automatically slowed (`detailSpeechRate`) and read digit-by-digit; `[[important]]` spans resist ordinary overlap for at most `protectedSpeechMaxMs` while explicit controls always win. Settings: `defaultSpeechRate`/`detailSpeechRate` (percent) + `protectedSpeechMaxMs` (see aokie-settings-schema.v1.json).
- Audio-corrected transcripts (optional; the `audioTranscript` setting — INDEPENDENT of `sendAudio` since 2026-07-17: either feature works alone; `audioTranscript` by itself still captures each caller turn's audio for the correction lane while the reply request stays text-only, and `sendAudio` by itself attaches turn audio to replies with no side-run corrections): after each caller turn (including a call-boundary flush) a small DETACHED request asks the audio-capable model to correct the on-device STT from the turn's audio — the reply path never waits on it (the correction is additionally submitted a couple of seconds AFTER the reply request, so it never contends for the model ahead of the caller's answer, and attached WAVs are silence-trimmed). A real correction emits the essential `aokie.call.turn.corrected {callId, turn, text, sttText, at}` (idempotency step `turn.<N>.corrected`); consumers UPDATE the stored turn in place and never treat it as a fresh caller turn. `aokie.call.ended` remains immediate for lifecycle consumers. The essential `aokie.call.transcript.settled` event repeats its terminal payload and adds `{transcriptSettledAt, transcriptCorrectionTimedOut}` only after every detached correction for that call reports back, or after the bounded 40-second deadline; summary/booking-analysis flows bind to this one-shot barrier so they read the corrected row without running twice. Desktop's headless dispatcher and the browser fallback both serialize app-logic + flow work per call correlation, so a correction write completes before settlement analysis. Graceful plugin/consent shutdown forces any pending barrier as timed out and waits for the outbox write; an abrupt process/OS/power failure between durable `call.ended` and settlement remains a documented gap because the delivery outbox cannot safely represent delayed internal work. The manager PIN gate consumes its turn before this machinery runs, so PIN audio is never sent for transcription. Unchanged/empty model output emits nothing. Optional settings `audioTranscriptEndpoint` (endpoint-classified URL) + `audioTranscriptModel` route corrections to a separate OpenAI-compatible server and/or a lighter audio model; both empty = the agent's own client/model.
- Selectable in-process TTS engine (2026-07-17): `ttsEngine` (`"" | pocket | sherpa`, applies live) picks which engine the synth worker loads — blank/`pocket` = Pocket-TTS (streaming chunks, voices `alba…marius` via `ttsVoice`), `sherpa` = statically-linked sherpa-onnx (Piper/VITS or Kokoro voice bundles; one-shot per span, RTF ≪ realtime; `ttsVoice` is a numeric speaker id there, anything else = the bundle default). `ttsModelDir` (string ≤400, applies live) points at the sherpa voice-bundle folder (`<name>.onnx` + `tokens.txt`, `espeak-ng-data/` inside the bundle or its parent, `voices.bin` marks Kokoro); blank = first usable bundle under `<app_data>/models/tts` (alphabetical). A change reloads the engine immediately via the synth worker (bad config logs and retries on the next span); the `ttsEndpoint` HTTP path still takes precedence over ANY in-process engine, with the same sticky per-call fallback. The startup loopback self-test exercises whichever engine is selected. Sherpa spans pass an attenuate-only loudness guard before the i16 conversion (peak ≤ 0.85, RMS ≤ 0.12 — un-normalized Piper/VITS output clips and its hotter far-end raised the AEC residual over the capture gates; live call 066d2237). The whole-object `settings.get` response carries a `ttsVoiceCatalog` side key (voice builds only; consumers must tolerate its absence): `{engines: [{id: "pocket", label, voices: [names…]}, {id: "sherpa", label, bundles: [{dir, name, kind: "vits"|"kokoro"}…], scanRoot}]}` — pocket voices are the installed preset basenames under `models/pocket_tts_onnx/voices`, sherpa bundles the valid voice folders under `models/tts` plus the configured `ttsModelDir` when it lives outside the scan root. Pure filesystem scan; the console's engine-first voice picker is its consumer.
- HTTP speech endpoints, OpenAI wire spec (2026-07-17, VOX-403/404): the `sttEndpoint` / `ttsEndpoint` settings accept ANY OpenAI-compatible speech server.
  - **STT** (`sttEndpoint`): `POST <url>` as `multipart/form-data` with part `file` (filename `audio.wav`, content-type `audio/wav`, 16 kHz mono PCM16 WAV of the utterance) + part `response_format` = `json`; the response is JSON `{"text": "…"}` (the `/v1/audio/transcriptions` shape). The legacy `{"audio": "data:audio/wav;base64,…"}` JSON body is GONE.
  - **TTS** (`ttsEndpoint`): the synth worker FIRST attempts a streaming-PCM request — `POST <url>` JSON `{"input", "voice", "response_format": "pcm"}`; a streaming server answers `200` with an `X-Sample-Rate` header and raw PCM16LE mono bytes in the body, which the plugin consumes INCREMENTALLY (~240 ms blocks, resampled per block to the SCO rate) so HTTP TTS is no longer a whole-utterance latency hit; aborting a span drops the connection (the server's cancel signal). A non-200 response or a missing `X-Sample-Rate` marks the endpoint non-streaming for the rest of the call and falls back to ONE whole-utterance request — `POST <url>` JSON `{"input", "voice", "response_format": "wav"}` accepting raw audio bytes (or, tolerated, JSON `{b64_json|audio}` base64) — the spec-compliant third-party path. A mid-stream failure BEFORE any audio shipped also takes the wav fallback; AFTER audio shipped the span fails honestly (re-synthesis would double-speak its prefix) and the sticky per-call in-process fallback engages as before. Rated (slowed) spans always use the whole-utterance path — WSOLA stretching wants the complete utterance.
  - **Gateway bearer**: when (and only when) an AI/STT/TTS endpoint's host:port is EXACTLY `127.0.0.1:17872` (the FormLogic desktop AI gateway), requests carry `Authorization: Bearer <FORMLOGIC_AI_GATEWAY_TOKEN>` from the environment — the token is never attached to any other endpoint.

## Phone link

- Pairing security (PAIR-001): SSP runs as NUMERIC COMPARISON — the radio advertises DisplayYesNo+MITM and HOLDS the confirmation (`phone.status.pairingConfirm` + the `aokie.phone.pairing_confirm_required` event) until the operator answers `phone.confirmPairing {address, accept}` (auto-refused after ~25s). Legacy fixed-PIN (0000) pairing is OFF unless the `legacyPairingPin` setting is explicitly on. Link keys are DPAPI-sealed at rest (pairing store v2; v1 plaintext migrates on load). `phone.removePaired` disconnects an active session for that device before dropping its key.
- Auto-connect (2026-07-17; `autoConnectPhone` setting, default ON, applies at radio start): once the dongle is initialised and no phone is on the line, the radio pages the last connected phone from OUR side (`phone.connect` semantics, HARD-001) so the receptionist comes up when the desktop app starts — no manual Reconnect. The target is the last address that actually connected (persisted to `plugin-data/aokie/last-phone.txt`), falling back to the sole bonded device (skipped when several are bonded — ambiguous). Because the outbound page can stall if the phone's stack is mid-teardown, it retries up to 6 times ~20-25s apart, then stops and leaves manual Reconnect. Setting OFF leaves the line requiring a manual `phone.connect`.

## Companion help and transfer

- Typed-help audit lifecycle: after the consent/fence-validated mailbox opens, the plugin durably emits one redacted `aokie.call.assistance.requested {requestId, callId, outcome:"requested", urgency:"normal", at}`. Consuming its accepted answer emits one `aokie.call.assistance.resolved` with `outcome:"answered"` and the authenticated `responderDeviceId`; timeout emits the same event with `outcome:"expired"` and no responder. Both use the request ID in their idempotency-key step. Question, context, answer and transcript content never enter these events.
- Owner transfer is an intent on that same volatile mailbox, advertised as `transferOffered:true`. A typed `decline` resolves it without interpreting answer text; acceptance is the ordinary prepared takeover claim and grants no audio authority by itself. Aokie remains the caller-audio owner while availability and native media are proved. Only the exact accepting device reaching `HumanActive` completes the transfer; declined, expired, or failed preparation returns to a deterministic keep-helping/message line under the current Aokie owner fence. Resolution audit outcomes are `declined`, `transferred`, `unavailable`, or `expired`, and remain content-free.
- Transfer on the OAIY route (`transfer_v1`, `docs/contracts/transfer/`): the realtime tool `transfer_to_owner {reason}` opens the same owner-transfer request for OAIY's call agent. The start offers it as `allowTransfer` (omitted when false) only for an inbound OAIY call when the host announced `ringPlan` in `plugin.init.features`, a Companion device is approved and consent currently grants both `remote_assistance` and `remote_takeover`; it exists for the session only if `ready.features` lists `transfer_v1`. The plugin asks the host `oaiy.ring.plan` (1.5 s; no answer means nobody is rung), aims the request at the planned devices (`request_transfer_to`: a device outside the plan is offered no takeover and cannot win or decline; a plan that toasts the desktop and names no device is `no_endpoint`: a toast is a notification, not a target, so a plan for the owner at the PC names the Windows Companion by thumbprint in `desktopCompanions`, running or not: nothing launches it, it is offered the request if it connects inside the ring window), and tells the host `oaiy.ring.opened`. The signed offer on the native call surface has a reserved id (`toffer_` plus 26 characters of base32 of SHA-256 of the request id and the device's endpoint thumbprint, with a generation counter that a retired offer increments). The tool answers `ringing` or a refusal at once; OAIY can withdraw an unwon request with `formlogic.realtime.transfer_cancel {requestId, reason: owner_declined|message_instead|gave_up}` on the same stream (answered by the `cancelled` outcome, or by a typed `transfer_notice` of `too_late` or `unknown_request` when nothing was withdrawn; replay-safe); the end arrives as `formlogic.realtime.transfer_outcome` (`accepted`, `declined` with the owner's bounded message, `unavailable`, `expired`, `cancelled`); a completed takeover sends no frame, the session stops with `handoff:takeover`, and the fresh session for the same call carries `start.resume {afterHandoff, handoffSeconds, via: "return"|"failback"}` and the return greeting. The audit events are the two above, with `cancelled` added as a resolution outcome. A tool call the plugin cannot run (a second slot tool, the 25th call of a call, an unknown name) is an `ok:false` result (`busy`, `tool_limit`, `unsupported`) and no longer ends the session.
